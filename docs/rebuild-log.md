# PCoM-DB 再構築 作業記録（2026年11月）

PCoM-DB（タンパク質共移動データベース）を Rails 7.1 から Rails 8.1 へ作り直した記録です。
技術ブログの素材として、判断の理由も残しています。

| | 再構築前 | 再構築後 |
|---|---|---|
| フレームワーク | Rails 7.1（2025年10月サポート終了）/ Ruby 3.3 | Rails 8.1 / Ruby 3.4（2028年3月まで） |
| Heroku スタック | heroku-22（2027年4月30日終了） | heroku-26（2031年4月末まで） |
| 依存 Gem の既知の脆弱性 | 246件 | 0件 |
| JavaScript ライブラリ | jQuery 1.8.2、Highcharts 4.0.3、Lightbox 2.7.1、Webpacker | Highcharts 12 のみ（残りは素の JS 約300行） |
| リポジトリ | 約1万7千ファイル（`node_modules`、秘密鍵、DB ファイル、ログを含む） | 約140ファイル |
| コントローラ | 約1,000行 | 約220行 |
| CSP | なし | `script-src 'self'`（インラインスクリプトなし） |
| テスト | なし | 自動テスト20件、旧ロジックとの全件照合 |

診断は2026年11月12日、作り直しから本番切り替えまでは11月15日の1日で行った。DB の変更は最後の索引追加と不要な空の表の削除だけで、データの行には一切触れていない。

## 2. バックアップの確認（第1段階）

- Heroku のダッシュボード（Durability タブ）から手動バックアップを取得。
- バックアップは PostgreSQL 17 の形式（アーカイブ形式 1.16）だったため、作業環境の

## 3. 見つかったバグ（本番で起きていたもの・起こり得たもの）

1. **メニューの背景画像などが表示されていなかった**
   CSS が `url(/assets/btn1.png)` と固定パスで画像を指定していた。
   Rails 4 以降、アセットはダイジェスト付きのファイル名（`btn1-5e26….png`）でしか出力されないため 404 に。
   メニュー以外にも、見出しの装飾、表の並べ替え矢印、トップページの背景画像、Overview の拡大画像が同じ原因で表示されていなかった。
2. **Help ページの PDF リンク**：リンク先のアクション（`helpdoc` など）にルートがなく、
   コード上はリンク生成の時点でエラーになる状態だった（本番での発生は未確認）。→ `public/excel/` の PDF に直接リンク。
3. **symbols 検索結果のリンク**：`GET /proteins/search_protein?gene_id=…` のルートがなく、
   クリックすると 404 だった。→ GET ルートを追加。
4. **複数検索で BP-1 を選ぶと色が付かない**：`gel64_*` の CSS クラスが未定義だった。→ 追加。
5. **パラメータが欠けると 500 エラー**：`gene_id_str` なしの getchart、`symbols` なしの検索など。→ すべて 404 か通常表示に。
6. **相同タンパク質の BP-1 行**：表示用の変数が未設定のまま参照する箇所があった（現データでは該当なし）。

## 4. 設計の判断（第2段階）

| 判断 | 理由 |
|---|---|
| Rails 8.1 で新規に骨組みを作り、コードを移植 | 7.1 → 8.1 の段階的アップグレードより、小さなアプリでは作り直しの方が確実で、不要な設定が残らない |
| **DB には一切変更を加えない** | 本番データを守るため。マイグレーションは置かず、`db/schema.rb` は本番のコピーから出力 |
| Webpacker・jQuery・Lightbox を廃止 | 依存ライブラリを減らす＝今後の更新作業を減らす。必要な処理は約300行の素の JavaScript（`pcom.js`）に置き換え |
| Highcharts は最新版（12.x）を同梱 | グラフの見た目と操作性を維持するため |
| インラインの `onclick` や `<script>` をすべて排除 | 厳格な CSP（`script-src 'self'`）を有効にするため。XSS があっても外部スクリプトを実行させない |
| 表の並べ替え（TINY.table.sorter）を書き直し | 元のコードは `new Function()` を使っており、厳格な CSP では動かないため |
| 1,000 行のコントローラを約 220 行に | `@msresults1`〜`30` のような繰り返しを、試料の一覧（`Material::ARABIDOPSIS_ROWS` など）による表示に変更 |
| `allow_browser`（古いブラウザを拒否する Rails 8 の既定）を外した | 研究者が古いブラウザで見ても閲覧できるように |
| 本番のホスト名を限定（`config.hosts`） | Host ヘッダ偽装・DNS リバインディング対策 |

## 5. 入力値の扱い

- 遺伝子 ID：前後の空白と全角空白を除去し、小文字化（旧サイトではブラウザ側だけで行っていた処理をサーバ側でも実施）。
- 64 文字を超える遺伝子 ID は無視する。グラフに重ねる遺伝子は最大 10 件までに制限（旧サイトはブラウザ側でのみ制限）。
- LIKE 検索の `%` や `_` は文字として扱う（`sanitize_sql_like`）。
- 存在しない試料 ID・遺伝子 ID は 404 を返す。

## 6. CSRF とグラフのクリック

グラフの点をクリックすると、同じフォームを別の URL（`getchartlist`）に送信する。
Rails は既定でフォームごとに URL に紐づいたトークンを使うため、送信先を変えると拒否される。
旧サイトはこの画面の CSRF 検証を外して対処していた。
新しい版では、このフォームだけ**セッション共通のトークン**を使うことで、検証を外さずに解決した。

## 8. 見た目の調整（リンクのデザイン）

- グラフ画面の外部リンク（TAIR、KEGG など）は見出し（`<h1>`）の中にあったため、見出しと同じ大きさの太字で、
  青い下線付きで表示されていた。これが古く見える原因だった。
- 3案を実際の画面に当てはめて比較し、**案C（控えめなテキストリンク）** を採用：
  - 外部リンクは小さな緑の文字で「・」区切り、外部サイトを示す「↗」付き。「link to」の文言は省略。
  - 一覧の遺伝子IDは濃い緑の等幅フォント、下線はマウスを乗せたときだけ。行全体も淡い緑で強調。
  - normal / max100% の切り替えも、薄すぎた灰色（#e0e0e0）から読める緑に。
- トップの表記を「Ver 2.2　last update:2026.11.16」に更新。

### gel_no / MW の表が空になる試料について

不具合ではなく、データの有無によるもの。分子量マーカーのデータ（materialweights）は
chloroplast、chloroplast 2、stroma、envelope の4試料には登録がなく、残りの9試料にだけある（マーカー4〜7か所）。

### 手元の確認で引っかかったこと（メモ）

production モードの確認で `assets:precompile` した `public/assets/` が残っていると、
開発サーバーがそちらを優先して配信し、CSS の変更が反映されないように見える。確認後は削除すること。

## 9. 照合テスト（第3段階）

### 手元での全件照合
旧コントローラの計算処理をそのまま写したスクリプトと、新しいアプリが返す HTML を、復元したバックアップで比較した。

| 対象 | 件数 | 不一致 |
|---|---|---|
| 色分けレベル（遺伝子×試料の全組み合わせ） | 11,708 | 10 |
| 試料ごとの一覧（13試料） | 13 | 0 |
| 一覧の symbols 表示 | 650 | 0 |
| グラフの値（各試料40遺伝子 × 2モード） | 1,040 | 6 |
| 複数遺伝子の重ね描き | 13 | 0 |
| ピークリスト（全試料の全 gel スライス） | 777 | 0 |
| 単一検索（相同タンパク質を含む） | 390 | 0 |
| 複数検索（大文字小文字・存在しない ID を含む） | 39 | 0 |

不一致はすべて、次の「並び順の不具合」によるもの。

### 旧サイトの不具合：gel の並びがずれていた10件
DB 上で行の保存順が gel 番号順になっていない組み合わせが10件あった（例：thylakoid の AT5G60250 は 57, 58, 59, 60, 1, 2, …）。
旧コードは `ORDER BY` なしで取得していたため、これらの遺伝子では**グラフと色分けの帯が途中で折り返して表示**されていた。
新しいコードは gel_no 順に並べるので正しく表示される（再発防止のテストも追加）。

対象：AT1G03110（chloroplast 2）、AT1G27680・AT1G64510・AT3G22380・AT5G16715・AT5G36700（stroma）、
AT5G60250（thylakoid）、sll1388・sll1813・slr0338（PCC6803）

### なぜずれたのか（原因）

DB の作り方の問題ではなく、旧アプリのプログラム側の問題だった。

- PostgreSQL の表は、行の保存順が保証されない。削除や更新で空いた場所に、あとから追加した行が詰めて保存されるため、
  時間がたつと保存順は登録順からずれる。バックアップでも、試料ごとの保存場所が入り組んでいた
  （例：chloroplast 2 のデータは表の先頭付近の空き場所に入っている）。
- 10件は、ちょうど空き場所の境目にまたがって保存された組み合わせ（例：stroma の AT5G36700 は gel 20〜56 と gel 1〜19 が別の場所）。
- 各行の ID は gel 番号順に正しく振られており、**データ自体は正しく登録されていた**。
- 旧アプリは `ORDER BY` を付けずに取り出していたため、保存順のまま描画されて折り返した。

教訓：**並び順が必要なら、必ず `ORDER BY` を書く**。新しいコードでは常に gel_no 順に並べ、テストで確認している。DB の修正は不要。

### 本番との照合（34回のアクセス、2秒間隔）
- 一覧 13試料：すべて一致
- グラフ 10件：7件一致。残り3件は上記の並びのずれで、**本番で実際にずれて表示されていることを確認**
- 単一検索・複数検索：一致（slr0338 の行のみ、上記のずれによる差）

### 相同タンパク質が複数ある場合
1つの試料に相同タンパク質が複数あるとき（Arabidopsis の628遺伝子が該当）、旧サイトは保存順で最後の1件だけを表示していた。
新しいコードも同じものを選ぶようにして、本番と一致させた（全件を表示する改善は今後の検討事項）。

## 11. 保守の自動化（第5段階）

- **GitHub Actions**（`.github/workflows/ci.yml`）：プルリクエスト、`master` への push、毎月1日、手動で実行。
  - Security：brakeman（コード解析）と bundler-audit（Gem の既知の脆弱性）
  - Tests：PostgreSQL 17 のコンテナに空のスキーマを作り、自動テストを実行
  - 月1回の定期実行で、コードを変えていなくても新しく公開された脆弱性に気づける
- **Dependabot**（`.github/dependabot.yml`）：Gem と GitHub Actions の更新を、月1回それぞれ1件のプルリクエストにまとめる。
  `master` へのマージ＝本番デプロイなので、自動マージはしない。
- Heroku の「Wait for GitHub checks to pass before deploy」を有効にすると、CI が成功した変更だけがデプロイされる（ただし「12. 自動デプロイが始まらなかった原因」の対策が必要だった）。
- 同梱している Highcharts（`vendor/assets/javascripts/highcharts.js`）は Dependabot の対象外。年1回程度、手動で更新を確認する。

## 12. 本番への切り替え（第6段階）

1. Heroku の「Wait for GitHub checks to pass before deploy」を有効化
2. Config Vars に `SECRET_KEY_BASE` を新規登録（旧アプリはリポジトリ内の `master.key` を使っていたため、設定が無かった）
3. スタックは heroku-22（Ruby 3.4.12 対応済み）。切り替え時の変更点を増やさないよう、スタック移行は後に分けた（「14. Heroku スタックの移行」）
4. DB には変更がないため、作業前に取ったバックアップで十分と判断
5. プルリクエスト #1 を `master` にマージ → CI 成功 → **自動デプロイが始まらず**、Heroku の「Deploy Branch」で手動デプロイ
6. 本番で確認：セキュリティヘッダ、404 処理、一覧・グラフ・点クリック・検索・画像表示・メニュー、ブラウザエラー0件。
   slr0338 のグラフが正しい位置（gel 45）に表示されることも確認

### 自動デプロイが始まらなかった原因

- Heroku の GitHub 連携自体は正常（手動デプロイ時に GitHub の Deployments へ記録が残っていた）。
- 「Wait for GitHub checks」は、コミットの**コミットステータス**がすべて `success` になるのを待つ。
- GitHub Actions は結果を**チェック（check run）**として記録し、コミットステータスは作らない。
- コミットステータスが1件も無いコミットは、GitHub 上で `pending` 扱いになる → Heroku は待ち続けた。
- 対策：CI の最後に、全ジョブの結果をコミットステータス（`ci/pcomdb`）として書き込むジョブを追加（プルリクエスト #2）。
  マージ後、手動操作なしで自動デプロイされることを確認した。

## 13. DB の改善（第7段階）

アプリの再構築では DB に一切手を付けなかったが、最後に2点だけ変更した。

| 変更 | 内容 |
|---|---|
| 索引の追加 | `msresults (gene_id, material_id, gel_no)`、`proteins (gene_id)`、`(search_gene_id)`、`(arabi_gene_id)` |
| 不要な表の削除 | `users`（昔のログイン機能の名残。本番で0件、アプリからは未使用） |

- 手元の測定（本番データの複製）：単一検索 280 ms → 34 ms、184 ms → 22 ms、グラフ 38 ms → 19 ms。索引の作成は約1秒、容量は約40MB。
- 適用方法：Rails のマイグレーションを Heroku の **release phase**（`Procfile` の `release: bin/rails db:migrate`）で実行。
  コマンド操作は不要で、マージ → CI → 自動デプロイの流れの中で適用される。マイグレーションが失敗した場合はデプロイ自体が中止され、旧版が動き続ける。
- 初回の適用で、Rails が管理用の小さな表 `ar_internal_metadata` を作る（1行）。
- `users` は、万一データが入っていたら削除せずに止まるようにした。
- 索引を追加すると DB が使う検索方法が変わるため、「相同タンパク質が複数あるときに保存順で最後のものを表示する」動作を、
  保存順（`ctid`）での並べ替えとして明示した。複製に適用したうえで全件照合を再実行し、不一致0件を確認。
- データの行数（msresults 712,250 / proteins 97,690 ほか）は適用前後で変化なし。

## 14. Heroku スタックの移行（heroku-22 → heroku-26）

- heroku-22 は2027年4月30日に提供終了。heroku-26（Ubuntu 26.04）は2026年5月から提供され、2031年4月末までサポート。
- ダッシュボードの「Upgrade Stack」は最新スタックに移す仕組みなので、heroku-24 を経由せず heroku-26 へ。Ruby 3.4.12 は heroku-26 にも対応。
- 手順：Settings →「Upgrade Stack」→ Deploy →「Deploy Branch」（スタック変更は次のビルドで反映される）。
- ビルドログの冒頭「Building on the Heroku-26 stack」「Changing stack from heroku-22 to heroku-26」で移行を確認。
  Settings の「heroku-26 will replace heroku-22 on the next deploy」という表示は、移行後もしばらく残っていた。
- 本番で全画面の動作を確認。問題があれば Activity の「Roll back to here」で heroku-22 のビルドに戻せる。
